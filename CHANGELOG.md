# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]
- Docker: `latest`, `X.Y.Z`, `X.Y`, `X` and `vX.Y.Z` are each one image for linux/amd64 and linux/arm64, from 0.11.0 on, and `docker/docker-compose.yml` and the Docker README use `ackingliu/pb-mapper:latest` on either architecture. `latest` used to hold one architecture, whichever was pushed last. The tags with an architecture suffix (`-x86_64_musl`, `-aarch64_musl`) remain.
- Save the app's settings, shares and connections whole. `config.json`, `services.json` and `clients.json` are replaced in one step, so a crash or power loss while saving leaves the old file or the new one, never a cut-off one. A file behind a symbolic link is still saved where the link points.
- Fix the relay holding on to a little memory for every temporary key that expired or was revoked, until it restarted, rotated its root key or reset its credentials. It now lets go of each within about 6 minutes of the key's expiry, even for a key revoked before then (a revoked key's row is kept until its expiry, as before).
- Fix `pb-mapper register` and `connect` missing a Ctrl-C pressed while they were handling a tunnel event or status change or writing the 30-second metrics line: on Linux and macOS it was ignored, and on Windows it ended the process at once, skipping the tunnel's orderly stop.
- Logs say more about what failed. `connect` says why it could not bind or accept on its local address (the operating system's error, such as a port in use); `register` logs a relay's refusal of a data stream as `relay refused the stream: <code>: <message>`; relay errors list their cause once, after the message, instead of repeating it inside. Events from reorganised modules name their submodule, such as `pb_mapper_server::runtime::lease` for what was `pb_mapper_server::runtime`, and the app's Logs page shows the longer names. A `RUST_LOG` filter on a crate or on a module's old path still matches, except for the administrator key's permission warning, which moved from `pb_mapper_auth::keys` to `pb_mapper_auth::persistence::admin_key`. An unreadable display-mode journal is logged once per change, not twice.
- Send each frame of an encrypted tunnel (`register --codec`, or encryption on in the app) over the relay's TCP carrier in one write instead of four (checksum, length, ciphertext, tag), so a small frame leaves as one TCP segment. The bytes on the wire are unchanged. In `relay_transport_bench` (relay and both ends in one process over loopback, Windows 11, Ryzen 9 9950X), the round trip of an 8-byte request fell from 431 to 197 µs at the median (p95 569 → 293 µs, p99 792 → 444 µs). Throughput and the QUIC carrier did not measurably change. See `docs/benchmarks/2026-11-11-refactor/`.
- SDK: breaking, so the next release is 0.12.0, not 0.11.x. The `pb-mapper` facade only gains items; the breaks are in the crates below it.
  - `pb-mapper-core`: `codec::Aes256GcmCodec`, `Aes256GcmEnCodec::new` and `Aes256GcmDeCodec::new` (use `try_new`), `Decryptor::decrypt_with_tag` (implementors drop it; callers use `decrypt`), `error::Error::MsgNetworkReadDatalen` and `config::init_tracing` are gone, and `config::StatusOp` no longer derives clap's `ValueEnum`; the crate no longer depends on clap or tracing-subscriber. New: `time`, `durable_file::{replace_contents, NewFileMode, ReplaceStep, ReplaceError}`, `test_support::{TEST_ADMIN_KEY, TEST_ADMIN_KEY_BYTES, TempPath}`, `RetryBackoff::MAX_DOUBLINGS`, and `config`'s `PB_MAPPER_TUNNEL_IDLE_TIMEOUT`, `PB_MAPPER_HALF_CLOSE_IDLE_TIMEOUT` and `PB_MAPPER_NEW_STREAMS_PER_SECOND` with their accessors.
  - `pb-mapper-protocol`: `secure::ServerInitialMessage` carries `first_flight: Option<FirstFlightProof>` in place of `replay_fingerprint` and `client_timestamp`, so `pb-mapper-server` 0.11.0 does not build against it. The `buffer` traits `BufferGetter`, `BufferedReader`, `DynamicSizeBuffer` and `FixedSizeBuffer` are gone (their methods are inherent on `CommonBuffer` and `BufferReader`: drop the imports), as are `forward::copy`, `forward::transfer_datagrams` and `MessageWriter::write_msg_mut`. New: `transport::UnknownLabel`, `as_str` and `FromStr` on `RelayTransport`, `as_str` on `SessionPath` and `SessionState`, and constants for the direct control timings, refusal codes and audit actions.
  - `pb-mapper-server`: `manager::TaskManager` is no longer generic (`new()`, `Default`), its `wait_for_task` returns an `Option`, its `get_conn_id` takes an iterator that is also `Clone`, and `TaskSender` carries `ManagerTask`, failing with `ManagerClosed` or `TrySendError`. `ConnMap`, `ForwardMessage`, `ManagedTask`, `MngWaitForTaskError`, `ConnTask::Forward` and `ConnTask::StatusResp` are gone, and `ManagerTask::Status` answers on a oneshot `response_sender`. New: `DirectServerConfig::{on_relay_port, probe_relay_port}`.
  - `pb-mapper-client`: `server::error::Error` gains `StreamRemoteError`, so an exhaustive match must add it. `Client::connect_tcp` reports a failure of its local socket pair as `Error::Io`, with the io error as its source, instead of `Error::Protocol`; the text is the same. `show_status_scoped` and `handle_status_cli_scoped` box a `client::error::FetchStatusError`, with the same text. New: `client::fetch_status_scoped`, which returns the status instead of printing it, and `FromStr` on `Transport`, `LegacyProtocol`, `PathPolicy`, `PortMapping` and `LanTransport` (and `as_str` on the first three), with their exact labels, failing with `UnknownLabel`, the same type as `RelayTransport`'s.
  - `pb-mapper-auth`: new `codes` (every `AuthFailure::code`), `ADMIN_SCHEMA_VERSION`, `ADMIN_KEY_FILE`, `admin_key_path`, and `AuthConfig::from_env_with(AuthConfigOverrides)`, which takes explicit settings over the environment without writing it. `pb-mapper-desktop`: new `valid_service`, and `Default` for `Adaptation` and `RateModel`.

## [0.11.0] - 2026-11-10
- Ask for the remote display's own size by default. A viewer that has not chosen a resolution asks for the remote display's own size, up to 4K, fitted inside the largest picture this device's decoder takes, instead of 1080p; 720p, 1080p and 1440p stay choices kept per computer, and the Display menu says how large the default goes on this device. A phone whose H.265 decoder stops at 1080p keeps H.265 and is sent 1080p. A computer remembered by an earlier version with 1080p reads as the default, since that version wrote 1080p whether it was chosen or not; choose 1080p again to keep it. Displays above 4K are still fitted into 3840×2160, a portrait display is still sent in landscape bounds, and 4K at 60 FPS has not been measured.
- Change the remote computer's resolution from the desktop viewer. While you control a Windows computer, **Display → Remote resolution** lists its display's modes and **Fit local**, which picks this display's size or the nearest it offers; **Original** puts its own back. The change is dynamic and never written to the registry. The host puts its mode back when the session ends, when control is revoked, or from **Restore** on its card, which says the resolution was changed; after a crash, the next start does it. A change the owner makes meanwhile is left alone. A remembered computer keeps Fit local and applies it again whenever you gain control. Phones do not offer it.
- Update the Windows desktop service once more: display modes need helper protocol 7 (`.v7` pipes), and **Update** installs it.
- Choose TCP for direct paths within a LAN. QUIC stays the default and the only carrier across the internet, punched or not. A consumer that sets **Settings → Direct connections → LAN transport → TCP** in the app, `--lan-transport tcp` on `connect`, `ConnectOptions::lan_transport` or Node `lanTransport: "tcp"` tries TCP on the LAN first, then QUIC on the LAN, then QUIC across the internet, then the relay; with LAN-first on, QUIC waits 300 ms for TCP. Remote-desktop connections take the same setting, and the viewer's path reads **LAN · TCP**. Publishers serve TCP by default and on demand (`--no-lan-tcp`, `RegisterOptions::lan_tcp`, Node `lanTcp: false` refuse it): the listener opens only when a consumer on the LAN first asks, on the direct port's number, and is offered on LAN addresses only. TCP uses the same per-session TLS 1.3 certificates and binding as QUIC, with its own ALPN and exporter label `pb-mapper/direct-tcp/1`, no tickets and no resumption. It needs the publisher's firewall to let TCP in, and nothing adds a rule; where it does not, the session takes QUIC on the LAN and TCP pauses (10 s, doubling to 5 min) without pausing direct. The wire gains one optional `PeerInfo.lan_tcp` and `LinkSummary.transport`, with no `DIRECT_VERSION` bump: an older relay, publisher or consumer leaves sessions on QUIC, byte-identical to before. Diagnostics report `transport` on links, `PathSelected` and session reports, `lan_transport`, `lan_tcp_sessions`/`active_lan_tcp`, and the `LanTcpMissed` event; path chips read **LAN · TCP**.
- The Rust SDK covers the whole remote desktop: `Host::watch` / `Viewer::watch` status streams; `desktop::supervisor::{RetryPolicy, Reconnect, Supervisor}`, the app's reconnect policy (backoff within 2 minutes, stalls, H.265 → H.264), which follows the viewer's own control wish; `DesktopView::display_point` and `Input::text_chunks`; `desktop::trust::{TrustFile, Sealer, CurrentUser, RelayScope, Remembered}` for a host identity kept across restarts, scoped by `Client::credential_namespace()`. Six examples (`desktop_loopback`, run in CI, `desktop_host`, `desktop_viewer`, `desktop_control`, `desktop_supervised`, `desktop_display_mode`), a Remote desktop section in the SDK README with how to decode, and docs.rs builds for Windows and Linux. Every entry point's default, LAN first, then direct, then the relay, is pinned by one test.
- The remote-desktop host is split by platform, with Windows behind a compile-time `Platform` and nothing above it naming an operating system, ready for Linux, macOS and Android ("Platforms" in `docs/remote-desktop.md` is the plug-in guide). A session's thread C runs on a concrete backend; the per-frame Windows calls are unchanged and measured within 3 % of before.
- Fix the app's native library reading a configuration, and applying its credential, before it was told its directory: it read the platform default at once (on a phone a relative `pb-mapper-ui` folder), so a process with a directory of its own, such as the acceptance tool, first loaded the desktop app's settings. It now reads nothing until `pb_mapper_set_app_dir`.
- Fix the Remote desktop host card showing the Windows desktop service's English text in red when the service is outdated, stopped, unverified, belongs to another installed copy of the app, or belongs to another Windows user: it now explains the state in the app's language and names the action that mends it on that card (stopping local sharing first where the service cannot be set up while it runs). The FFI reports these failures as typed error codes (`HELPER_OUTDATED`, `HELPER_STOPPED`, `HELPER_MISSING`, `HELPER_UNVERIFIED`, `HELPER_FOREIGN_APP`, `HELPER_OTHER_OWNER`), and the helper's status gains `owned_by_user`.
- Fix a remembered computer being saved under the relay and credential in Settings at the moment it was remembered, rather than those its session went through: a Settings change while a new computer waited for its first picture, or a credential the relay had not yet confirmed (saved as the administrator key), left it under the wrong relay scope, shown as on another relay. The record now takes the relay address and credential namespace from the live session as Rust connected it, as it already took the invitation, and `computers_remember` no longer accepts them from Dart.
- The app's remembered host grant also remembers the display's device name, and finds the display again after its id changed. An older app cannot read a grant saved by this one.
- SDK: breaking.
  - `Resolution::default()` is `Native`. `ViewerStatus` gains `modes`, `host_os` and `control_wanted`, `HostStatus` gains `display_mode`, `NoticeInfo` gains `seq`, `ViewerLink` gains `transport`, and `ViewerReason` gains `DisplayChanging`. New: `Decoders`, `ViewerConfig::for_decoders`, `VideoLimits::clamped`, `Viewer::set_display_mode` with `ModeTarget`, `ModeList`, `Mode` and `DisplayModeError`, `Host::restore_display_mode`, `recover_display_modes`. Desktop protocol: the `display_mode` capability, `display_mode` / `restore_display_mode` messages and the `display_mode_failed` notice, all offered only between ends that list the capability.
  - Hosts start with `Host::builder(HostOptions::new(service))…start(&client)` or `Host::start(&client, options)`, which replace the `start_*` constructors; `HostOptions` is `#[non_exhaustive]` and defaults to LAN first, then direct, then the relay, with `lan_tcp` on. `Host::{identity, restart_on, switch_display, rename}` and `privileged::background::adopt` take over what the app did itself. `host_support()` replaces `capabilities()`; Windows-only items move under `windows::{dpapi, media_foundation}` and `privileged::*` (was `helper`). `Backend` is reshaped, with typed `BackendError` / `FailureKind`. The FFI `capabilities` op adds `reason`.
  - `ConnectOptions`, `RegisterOptions`, `PeerInfo`, `LinkSummary` and `PathDiagnostics` gain fields, and `TunnelEventKind::PathSelected` a `transport`, so struct literals and exhaustive patterns must add them. `pb_mapper_update_config` takes a seventh parameter, `lan_transport`.
- Give one tenant several separately revocable keys. The administrator can now allocate a namespace (`admin namespace allocate`, `Admin::allocate_namespace`) and issue keys into it (`admin key issue --namespace`, `Admin::issue_key_in_namespace`). Those keys see the same services over TCP, QUIC and direct setup, revoking one leaves the others working, and the namespace outlives them. Namespace numbers cannot collide with a key's own namespace and are never handed out twice, including across root rotation and auth-state reset. A relay reports this as the `key_namespaces` capability, which `Admin::supports_key_namespaces` reads. Keys issued the old way, and state written by an older relay, stay in the namespace their key ID names. See `docs/authentication-v2.md`.
- Fix `key renew` with a shorter TTL: the new expiry was stored and refused new connections, but the key stayed active and its open connections stayed up until the old deadline, unless a restart happened first. The key now ends at the new deadline.
- Fix a renewal that landed as the key's old deadline passed: the renewal succeeded, then the old deadline ended the key anyway, and a restart brought it back because the log still said it was active. The key now stays active.
- Fix a crash during compaction sending the relay into safe mode, whose recovery ends every key. Log records for keys that had already gone are now skipped on replay.
- `admin service list` and `admin connection list` show a NAMESPACE column and take `--namespace`, which is what those values always were. `--key-id` still works and the JSON output is unchanged.
- Breaking for Rust SDK users: `IssuedKey`, `KeyMetadata` and `AuthStatusInfo` gain a field, so a struct literal must add it. Wire format changes are additive. An older relay refuses the two new requests without side effects, and an older client reads the new responses as before. A client older than this release that is given a key from a namespace fails every session to a direct-capable service, with no relay fallback: run it `--relay-only` or upgrade it.
- See and control another computer's screen from the app. A **Remote desktop** page sits between Tunnels and Relay (the **Remote** tab on a phone). On Windows, **Turn on remote control** installs the helper service once, with Windows' consent, and gives a private invitation, shown masked, copied, or offered as a QR code for a phone; the card says who is connected and can make them view-only, disconnect them or stop sharing. Another computer is added by pasting or scanning its invitation: the app shows the host and its fingerprint before connecting and refuses a pb-mapper setup string; on a desktop, paste and press Enter. The viewer takes the whole window. On a desktop it has a dark title bar and a floating toolbar with View and Control, Display, Shortcuts, connection quality and full screen; on a phone it is landscape and immersive, with its controls in the gutters beside the picture, a modifier bar over the keyboard, a minimap and an optional virtual mouse. **Back**, or a hidden or minimised window, keeps the session paused, for up to ten minutes. A lost connection is retried for up to two minutes, and the viewer says when the computer isn't sharing or another device is still viewing it. `desktop:` services no longer appear in Tunnels or the galaxy. On Windows without Media Foundation (N and KN editions without the Media Feature Pack, Windows Server without the Media Foundation feature), the app views remote desktops over JPEG and cannot share; the Remote desktop page says why. See `docs/remote-desktop.md`.
- Remember the computers you view. With **Remember this computer**, on by default, a computer joins the list once its first picture arrives and opens from it without its invitation. The invitations are kept by Rust in an encrypted vault, with DPAPI on Windows and an Android Keystore key on Android, and never return to the Dart side. The list shows which computers are online from the relay's own service list and keeps each one's last picture; on a phone, the featured computer's **More** renames, removes or remembers it. A computer whose host identity changed is never overwritten: only **Paste new invitation** replaces it, once the new session is remembered. Saved computers that can no longer be opened, such as after a Windows password reset or from a damaged file, are offered as **Clear saved computers**. Other platforms cannot remember computers yet.
- New touch gestures, compared with the PR #51 preview builds: a long press turns the finger's ball into a joystick — push it to scroll, faster the further it goes, or lift it where it is for a right click — and a two-finger tap no longer right-clicks; drag is a double tap whose second touch is held, then moved; three fingers also scroll, where the phone does not take three-finger swipes for itself; two fingers only pan and zoom the picture. On a phone the picture fits between the controls at its sides, which sit on dark strips so they stay legible over a white page, and a zoomed picture can be panned clear of them. Trackpad is the default mode and a tap clicks at once. A press that starts a drag waits out Windows' double-click time, so it never becomes a double click.
- Modifiers that cannot get stuck. Ctrl, Alt, Shift and Win on the phone's modifier bar apply to the next key or click when tapped once and stay on when tapped twice, and every key or click with modifiers goes as one sequence, so nothing is left held on the remote computer. A hardware keyboard's Ctrl+letter shortcuts reach it, AltGr characters type as characters, and the **Shortcuts** menu sends Win+D, Alt+Tab, Ctrl+Shift+Esc, the Start menu and Lock. Ctrl+Alt+Del is still unsupported, and keys outside the host's vocabulary, such as PrintScreen, Caps Lock, the Menu key and Ctrl with punctuation, are not sent.
- Know when this computer is being watched. While a viewer is connected, a capsule in the title bar, or a pill above a dialog, the setup screen or a full-screen viewer, offers **Disconnect viewer** and **Stop sharing**; so does the tray, whose icon and tooltip say who is watching. A window closed to the tray comes back, without taking focus, when a viewer arrives. **Quit** from the tray stops the app's own sharing first, so its viewer is told sharing stopped. Nothing shows a viewer while the Windows service shares with the app not running.
- On a phone, **Logs** moves into Settings: the bottom bar holds Overview, Tunnels, Remote, Relay and Settings.
- On Android 15 and earlier, Back on the main screen sends the app to the background, as Home does, instead of closing its window while its tunnels kept running without it.
- Open on the first page as soon as the app's own settings are read. A configured app no longer waits for the relay to answer first, which with an unreachable relay left only the backdrop on screen for up to 5 s.
- Remote desktop speaks desktop protocol v2 (ALPN `pb-mapper/desktop/2`). This version and the remote desktop preview builds (PR #51) cannot view each other: the connection fails at the handshake, never mid-session, and this version says the other computer runs a different pb-mapper version. Update pb-mapper on both computers. Invitations are now short `pbd1.` text; an invitation copied from a preview build still works, and still pins the same computer.
- Update the Windows desktop service once. A service installed by a preview build speaks an older helper protocol, so the Remote desktop page says the helper service needs an update; **Update** reinstalls it in place, with one Windows consent prompt, and keeps the saved background-sharing authorization and its invitation. **Turn on remote control** updates an outdated service in the same prompt that turns it on. A service installed from another build of the app, whose sharing code differs, is offered **Update** as well, and resuming sharing installs it first.
- Fix sharing after a relay change: turning remote control off and on again kept publishing this computer on the relay it was first set up with, so phones on the new relay never found it. Starting it again now uses the relay, credential and carrier in Settings. Because an invitation never moves to another relay by itself, the Remote desktop page says when this computer is still shared on another relay and offers **Share on the current relay**, which makes a new invitation for viewers to add again.
- Go direct over the local network first. When both ends share a Wi-Fi or LAN (the same IPv6 /64, or the same public address and private subnet), they try their LAN addresses first and use the first path that answers, instead of waiting for the next probe round; a computer's real LAN address is no longer crowded out by VPN, WSL or Hyper-V adapters. Nothing waits when the two are not on one network, and authentication is unchanged. Every direct link now reports what it is — LAN, internet or private, IPv4 or IPv6, how its address was learned, its QUIC round trip and how long setup took — in the SDK's diagnostics and events, the Node SDK, the app's path chips (**LAN**), tunnel diagnostics, the galaxy, the Relay page (with a rebuilt relay) and the remote viewer. iOS and macOS ask for local-network access.
- Turn LAN-first off when you need to. It stays on by default for every tunnel and for remote desktop. Off, setups probe the peer's addresses in the order it offered them, and nothing waits for the LAN. Either way the LAN is still detected and reported, and authentication is unchanged. On, a path off the LAN now waits for it (150 ms after answering) only when the LAN is known to be there: the same IPv6 /64, the same public address and private subnet, or a LAN address that has answered an authenticated probe. Two networks that merely use the same private subnet hold nothing back. The switch is **Settings → Direct connections → Try the local network first** in the app, saved at once without asking the relay. Running tunnels keep what they started with, and the app offers to restart the ones that may go direct. Elsewhere it is `--no-lan-first` on `register` and `connect`, `lan_first` in `RegisterOptions`, `ConnectOptions` and `HostOptions`, and `lanFirst` in Node requests. Background sharing carries it through helper protocol 5, so the Windows desktop service asks for **Update** once more. An old `config.json` reads as on. To compare the two behaviours, turn it off on both computers.
- Follow a tunnel's figures as they change, from the SDK. `Registration` and `Connection` gain `metrics()` and `subscribe_metrics(every)`, as do the remote desktop's `Host` and `Viewer` for the tunnel they run over, and `Client` gains `subscribe_relay_metrics(every)`. A sample covers:
  - sessions open now and in all, on the relay, direct and LAN;
  - application bytes each way on each of those paths, live while sessions run;
  - the relay's smoothed control round trip, from a share's heartbeat and a connection's probe;
  - the open direct link with QUIC's figures, including bytes, loss and bandwidth;
  - LANs found and missed;
  - the direct cooldown after a fallback, and the sessions it sent to the relay;
  - whether LAN-first is on.

  A stream samples at once, then each period and on every change, at least 100 ms apart. Its last sample comes after the tunnel stops. Nothing runs in the background. Both ends now count every session on the path it takes; before, a share never counted its relayed sessions and a relay-only connection counted none, so a share's path chip can now read **Relay** or both. Events now say which session opened or closed, with its link, and a closed one its duration and bytes. A fallback says why. A LAN found but not used is reported as `LanMissed`. The app's tunnel diagnostics refresh every second with the relay round trip, sessions and traffic per path. The CLI logs closed sessions and missed LANs, and logs metrics every 30 s. Node exposes all of it.
- SDK: breaking.
  - `TunnelEventKind` is `#[non_exhaustive]`.
  - `SessionOpened` and `SessionClosed` carry a session number and link; `SessionClosed` adds the duration and bytes.
  - `DirectFallback` carries a typed `FallbackReason`, which serializes as the old labels.
  - `LanDetected` gains `preferred`.
  - `ConnectOptions`, `RegisterOptions` and `HostOptions` gain `lan_first`, and a struct literal must add it. `..Default::default()` keeps it on.
  - `TunnelDiagnostics` gains `lan_first`, `traffic` and `relay_rtt_ms`.
  - `LinkStats` gains byte, loss and bandwidth figures.
  - `pb_mapper_update_config` takes a trailing `lan_first` argument.
- Steadier frame rate for remote desktop. A single Wi-Fi stall no longer drops the host to 10 FPS for ten seconds: the delay is judged on a median and a cut needs the receipts to show a real queue; short paths probe four times a second, and Balanced starts at its ceiling once the path answers quickly. A slow encoder or the Windows helper no longer halves the rate. The host keeps Windows timers fine while it streams, Android viewers always ask for 60 FPS, and Android shows video with two surface buffers, decoder hints and the screen's fastest refresh rate. The background service writes its sessions to a bounded `service-host.log`.
- The viewer's connection-quality panel shows every figure it has, in four groups: the network (path, network and stream round trips, bitrates), the picture (delay at each end; displayed, received and captured FPS), the host (preset and its FPS ceiling, pace, skipped captures, encoder time, adaptation) and the decoder (decoded and dropped per second, buffer timing, refresh rate). Quality keeps its 30 FPS ceiling, and the panel says so.
- SDK: breaking for exhaustive matches and struct literals. `PathDiagnostics` is `#[non_exhaustive]` and gains LAN counts and the open direct `link`; `TunnelEventKind` gains `LanDetected` and `PathSelected`; `SessionReport` gains an optional `link`, which an older relay drops.
- Remote desktop sends video on a new model. The host gets send credit back when the viewer's network task receives a frame, not when a phone shows it; capture paces evenly and adapts frame rate and bitrate to network delay, never resolution; keyframes come only on demand, and one slow to send never sets off another; and a viewer that falls behind keeps the newest frame and caps the host's frame rate. On Android, and on Windows with Media Foundation, the decoder pulls video from Rust itself, so H.264 never passes through Dart. Choose Quality, Balanced (the default: about 4 Mbit/s at 1080p, up to 60 FPS) or Smooth while connected. Phone fluidity is still being verified.
- Remote desktop uses H.265 when both ends' hardware has it, and H.264 otherwise. The host checks once per GPU for a hardware HEVC encoder. The viewer offers H.265 only where this device has a hardware HEVC decoder that takes the chosen resolution: on Windows that needs the HEVC Video Extensions and a GPU that decodes HEVC, on Android a hardware `video/hevc` decoder. The check never creates a decoder, and the viewer stops waiting for it after 2 s. H.265 uses the same bitrate as H.264, so the picture is sharper rather than the stream smaller. If the host's H.265 encoder fails, that computer uses H.264 until the app restarts. If a picture fails to decode as H.265, the viewer reconnects at once on H.264. Older builds still connect to this one, on H.264. **Display → Codec** chooses Auto (the default) or H.264 for this device.
- See the session's speed, as RustDesk shows it: everything the session moves each way, per second, as its tunnel counts it. The viewer's connection chip and the phone's quality button show the speed received. The quality panel adds the speed each way, the encoded resolution, and the codec with its chroma. An optional quality monitor shows the same few figures as RustDesk's, small and translucent over the picture: speed, frame rate, delay, target bitrate, codec, chroma and resolution. It is turned on from the viewer's menu, and the device remembers the setting.
- Choose each remembered computer's resolution and maximum frame rate.
  - **Resolution**: the remote display's own size up to 4K (the default), 720p, 1080p or 1440p.
  - **Maximum frame rate**: Auto, or 30, 60, 90 or 120, up to this display's refresh rate. A frame rate chosen over Auto replaces every preset's ceiling, Quality's 30 included.
  - Changing either reconnects at once.
  - The bitrate scales with the encoded size.
  - A size this device cannot decode is shown disabled, with the reason.
- The remote cursor now stays where the viewer puts it. Previously, the phone's arrow and its next stroke jumped back to a stale host position shortly after a move.
  - The host no longer reports the pointer moves it made for the controlling viewer. It reports every other change at once: the remote user's moves, a program's, or a clamp at a screen edge.
  - A report the host made before the viewer's latest move reached it no longer moves or hides the viewer's arrow.
  - The viewer's cursor belongs to the session, so it survives Back.
  - A last move refused because the picture was stale is sent with the next fresh picture.
- Update the Windows desktop service once more: it now speaks helper protocol 6, which carries H.265. The Remote desktop page offers **Update**.
- SDK: breaking for struct literals and exhaustive matches.
  - `ViewerConfig` gains `fps_override`.
  - `VideoCodec` gains `H265`. A viewer lists it in `ViewerConfig.codecs` beside H.264 or JPEG, never alone. The SDK sends it to the host as the `h265` capability, so an older host never sees it.
  - `Resolution` names the four sizes, and `VideoLimits::choose(refresh_hz, resolution, max_fps)` derives limits from them.
  - `ViewerStats` gains `speed_rx_bps` and `speed_tx_bps`.

## [0.2.19] - 2026-08-15

The row offered Connect in that state, so a failing tunnel retried indefinitely with nothing in the interface able to stop it.
- Fixed connecting reporting success before it had connected. Accepting the request and coming up are different events, and only the first had a message, so a green "client connection started" appeared while the client was failing to reach the server. The settled result now gets its own message, in red, with the reason beneath it.
- Split Operations into Status, Services and Config. The status page carried both the server's state and the list of registered services side by side, which put the longer of the two — the one you scroll — into half a window.
- Added the connections a service is actually holding, on the Services page. Expanding a key lists each control connection with its id, how long since it was last heard from, its generation, its protocol version, and whether the server considers it healthy. This information was previously shown as a Rust debug dump of the whole connection map.
- Added selection and one-click copying for service keys and connection ids, and made the whole row open rather than just its chevron.
- Replaced the notification bar with stacking toasts. The previous one showed a single message at a time, replaced it mid-read when another arrived, and could not be dismissed. Errors now stay until closed; everything else clears itself.
